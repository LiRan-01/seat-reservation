## 2. 负责范围与实现检查要点

| 工作项 | 报告中的实现要点 | 验证关注点 |
| --- | --- | --- |
| 创建预约与并发控制 | 事务内对座位加行锁，检查时段冲突与信用门槛，写入预约并生成签到码；唯一约束兜底 | 同一座位、重叠时段不能同时预约成功；业务冲突不应表现为服务器异常 |
| 签到与防重放 | 验证签名、签到窗口和一次性随机数，更新预约及座位状态 | 窗口外签到被拒绝，同一码重复使用被拦截，失败请求不应把座位改为使用中 |
| 暂离与返回 | 在使用中与暂离之间进行状态切换 | 返回后前端与后端状态一致，暂离超时进入释放与违规处理流程 |
| 超时释放任务 | 每分钟扫描，单批 500 条；通过状态条件更新判断是否已处理 | 同一预约重复扫描不应重复扣分、重复记违规或重复通知 |
| 部署与联调 | Docker Compose 启动依赖和服务，初始化脚本提供自习室及座位数据 | 服务可访问，基础数据完整，前后端接口与数据库记录一致 |

预约冲突要同时检查接口响应与最终数据，不能只凭页面提示判断是否超卖。定时任务也应检查预约状态、座位状态、信用变化、违规记录和候补通知是否相互一致。

## 3. 环境与复现入口

报告记录的测试环境为 GitHub Actions 托管运行器（2 核、7 GB），应用、MySQL、Redis 与前端同机部署。主要技术包括 JDK 17、Spring Boot 3.2.5、MySQL 8.0.36、Redis 7.2、Vue 3 和 Vite。

在具备 Docker Compose 和 Bash 的项目环境中，原补充记录给出的执行入口为：

```bash
# 在项目根目录启动全栈环境
docker compose up -d --build

# 功能验收：输出逐项 PASS/FAIL
bash scripts/acceptance-test.sh

# 并发与性能：输出请求统计、响应时间和超卖情况
bash scripts/perf-test.sh
```

执行前先检查容器状态、启动日志和数据库初始化结果，确认服务已就绪。Windows 使用 Git Bash、WSL 或 Codespaces 执行 Bash 脚本；实际入口与端口以当前仓库配置为准。

复测应记录提交 SHA、运行环境、执行时间及日志位置，并注明测试数据的准备方式。需要构造预约或修改数据的测试，应使用独立测试环境。

## 5. 并发与性能结果整理

| 测试场景 | 负载 | 判断标准 | 既有实测结果 | 结论 |
| --- | --- | --- | --- | --- |
| 并发抢座 | 200 次请求、40 并发，竞争 40 个座位 | 成功数不超过可用座位数，无超卖 | 成功 40、冲突 160、超卖 0 | 该轮负载下未发现超卖 |
| 座位图查询 | 150 次请求、30 并发 | P95 不超过 200 ms | P50 204 ms、P95 310 ms | 未达到目标 |
| 签到接口 | 40 并发 | P95 不超过 300 ms | P50 29 ms、P95 49 ms | 该轮达到目标 |
| 定时任务 | 单批处理 500 条过期预约 | 单批不超过 40 秒 | 883 ms | 该轮达到目标 |

P50 为中位响应时间，P95 表示约 95% 的请求响应时间不超过该值。比较不同轮次时应保持环境、数据量、并发数和测量方式一致。

抢座结果需要核对成功响应数与数据库中的有效预约数是否一致，同时检查冲突响应和服务器错误数量。200 次请求的总量不等于 200 并发；本轮报告标注的并发数为 40。

座位图查询 P95 为 310 ms，不能写成“全部性能指标达标”。报告将问题归因为按座位逐条查询占用情况造成 N+1 查询，并登记为 BUG-05。按房间批量查询占用区间是报告提出的优化方向，是否修复及是否达标仍需代码与新一轮日志确认。

## 6. 异常、边界与待验证项目

| 编号 | 场景 | 既有材料记录 | 后续核查重点 |
| --- | --- | --- | --- |
| ET-01 | 重复提交预约 | 报告记录通过 | 同一业务请求重复发送，核对只生成一张预约单 |
| ET-02 | 签到码重复使用 | 报告记录第二次使用被拒绝 | 核对拒绝原因、签到次数与日志；防重放结果不能单独证明首次扫码者的身份 |
| ET-03 | 服务器时间漂移 | 报告表 20 写明调快容器时间并通过；原补充记录说明只做了逻辑校验 | 两份材料口径不一致，暂列待专项验证，不能认定已完成真实环境时间漂移测试 |
| ET-04 | 跨天预约 | 报告记录 23:30—次日 00:30 场景通过 | 检查自然日切分、跨天查询及相邻时段是否正确 |
| ET-05 | 释放后立即再约 | 报告记录通过 | 同时请求仅允许符合规则的一方取得预约，核对另一方及候补状态 |
| ET-06 | 任务执行延迟 | 报告记录通过；原补充记录说明用人为阻塞验证顺延逻辑 | 保存延迟、顺延和信用变化日志；长时间稳定性尚需单独验证 |

补充回归设计：签到窗口开始前后、结束前后各取临界值；暂离满 30 分钟前后检查超时判定；对已释放预约重复运行任务；强制释放后尝试使用原签到码。这些属于后续检查清单，本次未执行，不填写“通过”。

## 7. 缺陷与修复后的回归重点

以下 BUG 编号沿用报告表 21，状态为报告记录。

| 编号 | 问题 | 报告状态与处理 | 回归检查重点 |
| --- | --- | --- | --- |
| BUG-01 | 同一预约被扣两次信用分 | 已修复；改为状态条件更新并检查影响行数 | 重复触发或并发触发任务，只生成一次违规及一次扣分 |
| BUG-02 | 暂离返回后页面仍显示暂离 | 已修复；失效缓存后重新拉取 | 返回后页面、接口与数据库状态一致 |
| BUG-03 | 签到窗口前后判定偏差一分钟 | 已修复；引入统一时钟组件 | 使用固定时钟检查窗口临界值；真实时间漂移另行验证 |
| BUG-04 | 强制释放后原预约仍可签到 | 已修复；释放同步更新预约并校验状态 | 原签到码不能恢复已释放预约或重新占用座位 |
| BUG-05 | 座位图 P95 达 310 ms | 待修复；拟减少 N+1 查询 | 同负载复测 P95，同时核对返回状态是否正确 |

原《功能与并发测试记录》还记载了两项联调问题，未在这里擅自新增 BUG 编号：

- **唯一键冲突返回 500**：原记录称已映射为 HTTP 409 与 `TIME_CONFLICT`。复测时应分别统计成功、业务冲突及其他错误，确认冲突不会被误计为服务器异常。
- **第二自习室初始化座位缺失**：原记录称已改为显式主键分配，A 区 1—20、B 区 21—40。复测应分别查询两个自习室、核对座位数量和标识，并验证 B 区可以完成预约。

## 9. 结论与后续工作

依据附件中的既有记录，核心预约与签到流程在该轮测试中可以完成，200 次抢座请求没有出现超卖；签到接口和定时任务达到当轮设定阈值，座位图查询未达到性能目标。

后续优先核对 BUG-05 的当前修复状态，并按相同负载复测。服务器时间漂移需要补充可复核的专项证据，任务长时间稳定性与前端自动化 UI 测试也仍有待完善。当前材料不足以据此宣称生产环境稳定性或所有边界场景均已验证。

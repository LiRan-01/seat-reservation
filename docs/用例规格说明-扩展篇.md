## 一、UC-04 暂离与返回

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-04 |
| 参与者 | 学生 |
| 前置条件 | 存在状态为"使用中"（USING）的预约单 |
| 触发条件 | 学生在使用中点击"暂离"或"返回" |
| 基本流 | 1. 学生提交暂离请求，携带暂离分钟数（默认 30）；2. 系统校验预约状态必须为 USING；3. 预约置为 AWAY，写入暂离截止时间 `awayUntil = 当前时间 + min(分钟数, 30)`；4. 座位状态同步置为 AWAY；5. 学生返回时提交返回请求；6. 系统校验状态为 AWAY，置回 USING 并清空 `awayUntil`；7. 座位状态恢复 USING |
| 异常流 A1 | 当前不是使用中（已暂离、已终止或未签到）：返回 `STATUS_INVALID`，提示"只有使用中的预约可以暂离" |
| 异常流 A2 | 当前不是暂离状态就点返回：返回 `STATUS_INVALID`，提示"当前不是暂离状态" |
| 异常流 A3 | 暂离已超时被定时任务判为 `NO_SHOW`：预约进入终态，再点返回同样返回 `STATUS_INVALID`，需重新预约 |
| 后置条件 | 暂离期间座位不释放、不对他人开放；返回后恢复使用中；超时则由 UC-09 接管 |

**设计说明**：暂离上限在服务层用 `Math.min(minutes, 30)` 硬性截断，即使前端传 120 分钟也只生效 30 分钟。截断而不是报错，是因为学生点"暂离 2 小时"在语义上等于"我要走了"，截断到上限后由超时逻辑回收，比直接拒绝更符合真实行为。需要提醒的是，配置项 `app.away-max-minutes` 虽然写了 30，但代码并未读取它，改配置不生效（见《需求与用例补充说明》第七节）。

## 二、UC-05 候补登记

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-05 |
| 参与者 | 学生（主）、系统定时任务（间接） |
| 前置条件 | 目标座位存在；目标时段已被他人预约或正在使用（这是触发候补的条件） |
| 触发条件 | 学生在座位图上对不可用座位选择"候补" |
| 基本流 | 1. 学生提交候补请求，携带座位、学号与目标时段；2. 系统确认该学号在信用表中有记录，无则初始化 100 分（外键要求）；3. 写入候补记录，状态为"未通知"；4. 座位释放时（取消、结束、强制释放、超时释放）触发通知：取该座位最早一条未通知记录，标记为已通知，写入站内通知（标题"候补叫号提醒"），并输出日志；5. 学生通过 UC-13 查看通知 |
| 异常流 A1 | 座位不存在：返回 `SEAT_NOT_FOUND` |
| 异常流 A2 | 同一学生对同一座位重复登记：**当前未拦截**，会写入多条候补记录，相当于自己占多个排队位；被通知时只取最早一条，其余仍留在队列里 |
| 异常流 A3 | 通知发出后学生未在时段内预约：**当前不回收候补资格**，记录被标记为已通知即退出队列，不占用名额，也不会自动顺延给下一位 |
| 后置条件 | 候补记录留痕；被通知者收到一条站内通知；座位仍为空闲，先到先得 |

**两处没做到的**：重复登记未去重（A2）、通知后未顺延（A3）。前者是遗漏，后者是取舍——自动顺延需要给"被通知者"设置响应时限（例如 10 分钟未预约就轮给下一位），这套超时逻辑与预约超时是两套时钟，本期没有做。演示版里候补的实际效果是"通知到位，不保证轮到"，报告正文没有夸大这一点。

## 三、UC-07 强制释放

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-07 |
| 参与者 | 管理员（主）、学生（被处置方） |
| 前置条件 | 存在非终态的预约单；管理员已完成现场核验 |
| 触发条件 | 管理员在系统中对该预约执行强制释放，并填写处置原因 |
| 基本流 | 1. 管理员提交释放请求，携带预约号与原因（默认"现场核实"）；2. 系统校验预约不处于终态；3. 以带状态条件的更新把预约置为 `FORCED`，影响行数为 1 才继续；4. 座位状态置为 AVAILABLE；5. 通知该座位的候补队列首位；6. 返回更新后的预约单 |
| 异常流 A1 | 预约已是终态（已结束、已取消、已超时）：返回 `STATUS_INVALID`，提示"该预约已是终态" |
| 异常流 A2 | 并发下状态已被其他请求改变：条件更新影响行数为 0，返回 `STATUS_INVALID`，提示刷新后重试 |
| 异常流 A3 | 学生持原签到码再来签到：条件更新要求状态为 RESERVED，影响行数为 0，返回 `STATUS_INVALID`，引导重新选座 |
| 后置条件 | 预约为终态 FORCED，座位回到可用，候补收到通知；**不写违规记录、不扣信用分** |

**为什么不计违规**：强制释放的判断依据是管理员现场核验，存在误判可能（学生只是去接水、书放着人没走远）。罚错比不罚更难收拾，所以实现选择只释放、不罚分。这与早期用例描述"强制释放并计违规"不同，属于实现阶段的产品决策，已在《需求与用例补充说明》第四节更正。

## 四、UC-08 查看统计

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-08 |
| 参与者 | 管理员 |
| 前置条件 | 无（只读） |
| 触发条件 | 管理员按日期区间查询上座率 |
| 基本流 | 1. 管理员提交起止日期（`from`、`to`，形如 `2026-11-27`，两项均必填）；2. 系统逐日统计：取当日 08:00—22:00 开始的预约，剔除终态中的已结束、强制释放、爽约三类；3. 对每条有效预约按日窗口裁剪占用时长并累加；4. 上座率 = 占用座时 ÷（座位总数 × 14 小时）；5. 返回每日的日期、有效预约数、占用座时、可用座时与上座率 |
| 异常流 A1 | 缺少 `from` 或 `to`：Spring 返回 400，提示参数缺失 |
| 异常流 A2 | 日期格式非 `yyyy-MM-dd`：返回 400 参数解析失败 |
| 后置条件 | 只读，不改变任何状态 |

**口径上的两个已知偏差**：

1. **已取消的预约被计入有效**。过滤条件只剔除了 `RELEASED`、`FORCED`、`NO_SHOW`，没有排除 `CANCELLED`。学生约了又取消，仍会被算进占用座时，上座率偏高。
2. **跨天预约不计入**。统计按"开始时间落在当日 08:00—22:00"筛选，23:30 开始、次日 00:30 结束的预约在两天里都不出现。

这两条都不影响功能验收（FT-10 只校验接口返回结构），但对外报数时要注意口径。另外，接口文档里写的路径参数是 `?date=`，实际实现是 `?from=&to=`，以代码为准。

## 五、UC-10 统一身份认证（演示版）

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-10 |
| 参与者 | 统一身份认证平台（外部系统，正式版）／学生本人（演示版） |
| 前置条件 | 无 |
| 触发条件 | 学生使用系统前的身份确认 |
| 基本流（演示版） | 1. 学生在前端填写学号；2. 后续所有请求以 `userId` 参数携带学号；3. 服务端信任该参数，不做校验；4. 信用记录、预约单、通知均以学号为主键关联 |
| 基本流（正式版，未实现） | 1. 跳转学校统一身份认证；2. 认证通过后返回学号与票据；3. 服务端校验票据并建立会话；4. 后续请求以会话标识身份，不接受客户端传入的学号 |
| 异常流 A1 | 学号未填写：前端提示先设置学号；后端在缺少 `userId` 时返回参数错误 |
| 异常流 A2 | 学号在信用表中不存在：预约时自动初始化一条 100 分记录，不报错 |
| 后置条件 | 演示版不产生任何会话状态 |

**这条用例的边界必须说清**：演示版没有鉴权，任何人传入别人的学号都能查预约、取消预约（取消接口在 `userId` 为空时还会跳过归属校验）。这在课程演示环境里可以接受，但绝不能当成"已实现身份认证"。系统把认证整个交给了外部平台，本期只做了"以学号标识用户"这一件事。

## 六、UC-11 用户取消

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-11 |
| 参与者 | 学生 |
| 前置条件 | 存在状态为"已预约"（RESERVED）的预约单，尚未签到 |
| 触发条件 | 学生在"我的预约"或预约单卡片上点击取消 |
| 基本流 | 1. 学生提交取消请求，携带预约号与本人学号；2. 系统校验预约归属为该学号；3. 校验状态必须为 RESERVED；4. 条件更新置为 `CANCELLED`；5. 座位回 AVAILABLE，通知候补首位；6. 返回更新后的预约单 |
| 异常流 A1 | 预约不属于该学号：返回 `USER_MISMATCH`，提示只能取消本人预约 |
| 异常流 A2 | 已签到（USING／AWAY）或已终态：返回 `STATUS_INVALID`，提示只有未签到的预约可以取消 |
| 异常流 A3 | 并发下已被定时任务判为爽约：条件更新影响行数为 0，返回 `STATUS_INVALID` |
| 后置条件 | 座位释放、候补受通知；**不扣分**，取消是正当行为 |

**一个越权口子**：归属校验写的是"当 `userId` 不为空时才校验"，即请求不带 `userId` 就能取消任何人的预约。接口文档要求必须传，前端也一直传，但服务端没有强制。演示环境无鉴权，风险有限；正式版必须改为强制校验。

## 七、UC-12 正常结束

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-12 |
| 参与者 | 学生 |
| 前置条件 | 存在非终态的预约单 |
| 触发条件 | 学生提前离开，点击"结束使用" |
| 基本流 | 1. 学生提交结束请求；2. 系统校验预约不处于终态，并记录当前状态；3. 以带状态条件的更新把预约置为 `RELEASED`；4. 座位回 AVAILABLE；5. 通知候补首位；6. 返回更新后的预约单 |
| 异常流 A1 | 预约已是终态：返回 `STATUS_INVALID` |
| 异常流 A2 | 并发下状态已变化：条件更新影响行数为 0，返回 `STATUS_INVALID` |
| 后置条件 | 预约为终态 RELEASED，不计违规、不扣分 |

**与 UC-11 的边界**：两条用例都会把座位释放掉，区别在终态语义——未签到就放弃叫"取消"（CANCELLED），用过之后离开叫"结束"（RELEASED）。当前实现允许对"未签到"的预约调结束接口，此时会落成 RELEASED 而不是 CANCELLED，统计口径里两者待遇不同（CANCELLED 未被排除，见 UC-08）。规范做法是结束接口只接受 USING／AWAY 状态，这条留作后续修正。

## 八、UC-13 查看通知

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-13 |
| 参与者 | 学生 |
| 前置条件 | 前端已设置学号 |
| 触发条件 | 学生点击"查看通知"，或候补叫号后主动查看 |
| 基本流 | 1. 按学号查询该用户的站内通知；2. 返回通知列表，每条含类型、标题、内容、关联座位、是否已读、创建时间；3. 前端按未读高亮展示 |
| 异常流 A1 | 该学号无通知：返回空列表，前端不渲染通知区块 |
| 异常流 A2 | 学号缺失：返回参数错误 |
| 后置条件 | 只读。**本期不提供"标记已读"接口**，`read` 字段始终为未读 |

通知目前只有一个来源：候补叫号（类型 `WAIT_NOTIFY`）。超时释放、强制释放都不通知被处置的学生，只在后台日志留痕——这是本期的缺口，学生只能自己回来看预约状态才知道座位没了。

## 九、用例之间的关系

报告 3.2.2 用一段话交代了包含、扩展与泛化关系，这里落实为清单，方便逐条对照用例图：

| 关系 | 基用例 | 目标用例 | 触发条件 | 说明 |
|---|---|---|---|---|
| 包含 <<include>> | UC-02 创建预约 | 签到码签发 | 必然执行 | 预约成功即生成令牌，无令牌无法签到 |
| 包含 <<include>> | UC-03 扫码签到 | 令牌验签 | 必然执行 | 验签失败直接终止，不进入后续步骤 |
| 包含 <<include>> | UC-09 自动超时释放 | UC-05 的候补通知 | 释放成功即执行 | 释放后通知该座位候补首位 |
| 扩展 <<extend>> | UC-02 创建预约 | UC-05 候补登记 | 目标座位该时段不可约 | 不可约时才出现候补入口 |
| 扩展 <<extend>> | 预约生命周期 | UC-04 暂离与返回 | 使用中学生临时离开 | 不满足条件时主流程照常 |
| 扩展 <<extend>> | 预约生命周期 | UC-11 用户取消 | 未签到且学生主动放弃 | 可选路径 |
| 扩展 <<extend>> | 预约生命周期 | UC-12 正常结束 | 学生提前离开 | 可选路径 |
| 泛化 | UC-10 统一身份认证 | 演示版学号标识／正式版平台对接 | 部署形态不同 | 两种实现，本期只有前者 |
| 泛化 | UC-03 扫码签到 | 手机扫码／自助机读卡 | 设备不同 | 令牌相同，只是采集方式不同 |

把这九条关系摊开看，会发现一个结构特征：**所有扩展都挂在"预约生命周期"这条主干上**，主干只有一条（RESERVED → USING → 终态），扩展节点都在主干之外。这正是状态机设计能收敛到一张表的原因，也是第4章状态图只有五个状态的原因。

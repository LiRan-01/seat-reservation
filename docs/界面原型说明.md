# 学生端界面原型说明

> 撰写：冯诗祺（需求分析与用例建模）
> 实现位置：`frontend/src/App.vue`（单文件组件）、`frontend/src/style.css`
> 对应报告：3.2 用例模型的界面落地；表11 中"兼容性"一条的验证对象

## 一、为什么是一个单页

原型阶段考虑过拆成三个页面（选座页、我的预约、通知），最后压成一个单页。理由不是省事，是**状态太少**：整个演示过程只有"一张预约单"处于活跃状态，页面之间跳转反而会把它弄丢——学生在座位图点完座，跳到"我的预约"才知道预约号，再跳回来扫码，中间任何一次刷新都要重新找。

单页把这条链路的上下文固定在一屏之内：顶部是筛选条件，中间是座位图，下方是当前预约单卡片，再下方是通知。滚动即可看到全部，不用记"我刚才约的是哪个座位"。

代价是没有多单管理：同一学生约了第二个座位，第一张卡片就被覆盖，只能去接口查。这在真实场景里不可接受，在演示里可以。

## 二、页面结构

自上而下五块，都是条件渲染：

| 区块 | 内容 | 渲染条件 | 对应用例 |
|---|---|---|---|
| 页头 | 标题与一句话流程说明（选座 → 预约 → 扫码签到 → 暂离/超时释放） | 常驻 | — |
| 筛选栏 | 自习室下拉、起止时间（`datetime-local`）、学号输入、刷新按钮、查看通知按钮、右侧"空闲 X / Y" | 常驻 | UC-01、UC-06、UC-13 |
| 提示条 | 单行消息（预约成功、冲突原因、签到结果等），蓝底左边框 | 有消息时 | 全部用例的反馈 |
| 图例 | 五色说明：空闲、该时段已预约、使用中、暂离、停用 | 常驻 | UC-01 |
| 座位网格 | 10 列网格，每格显示座位编号（A-01）与特征（靠窗/插座），点击即下单 | 常驻 | UC-01、UC-02 |
| 预约单卡片 | 预约号与状态、签到码（等宽字体折行显示）、五个动作按钮 | 有活跃预约单时 | UC-03、UC-04、UC-11、UC-12 |
| 通知区 | 通知标题、内容、时间，未读项蓝底左边框 | 通知列表非空时 | UC-13 |

## 三、五种座位状态的视觉编码

状态用"底色 + 边框 + 纹理"三重编码，不只靠颜色，避免色觉障碍者无法区分：

| 状态 | 视觉 | 色值 | 是否可点 |
|---|---|---|---|
| 空闲 | 白底细灰边 | `#ffffff` / `#c9cdd4` | 可点，点击下单 |
| 该时段已预约 | 红底红边 | `#fbccc7` / `#f98981` | 不可点，点击提示"该时段已被预约" |
| 使用中 | 绿底绿边 | `#b7e3c2` / `#4ec26d` | 可点（实际会返回冲突，见第五节） |
| 暂离 | 黄底 45° 斜纹 | `#ffe7ba` / `#f7ba1e` | 可点（同上） |
| 停用 | 灰底灰字 | `#e5e6eb` | 不可点 |

红色代表"已被占"、绿色代表"正在被用"，这个编码是从图书馆座位图沿用下来的，学生不用学。斜纹专门留给暂离：暂离既不是空闲也不是正常的"使用中"，斜纹表达"暂时保留、随时可能回来"，比单纯换个颜色更能传达"别去抢"。

## 四、主流程的交互路径

```
选自习室/时段 → 座位图刷新（GET /api/rooms/{id}/seats）
      ↓ 点空闲座位
POST /api/reservations → 预约单卡片出现（状态 RESERVED，显示签到码）
      ↓ 点"模拟扫码签到"
POST /api/checkin → 状态 USING，座位变绿
      ↓ 点"暂离 30 分钟"          ↓ 点"结束使用"
POST /away → AWAY，座位变斜纹     POST /finish → RELEASED，座位变白，卡片停留
      ↓ 点"返回座位"
POST /back → USING，座位变绿
```

卡片上的按钮不随状态禁用，全部常亮。好处是演示时不用解释"为什么按钮灰了"，坏处是误点会拿到 `STATUS_INVALID` 的报错——例如已签到的预约再点"取消"。这些报错都来自服务端校验，前端没有做状态互斥，等于把状态机的可见性完全交给了提示条。

## 五、三处交互设计上的问题

**1. 点击座位即下单，没有二次确认。** 这是最严重的一处：手滑点到相邻座位就直接产生一条预约，而系统**没有当日预约次数上限**（见《需求与用例补充说明》第六节），意味着可以无成本地连点出一串预约，把座位全占住。演示时不会有人乱点，真实投用第一天就会出问题。改法很简单：点击后弹出"确认预约 A-07，08:00—12:00"的确认条，或者在卡片区显示"已选中，确认提交"。

**2. 签到码明文显示。** 演示环境把签到码直接铺在卡片上，点"模拟扫码签到"完成 UC-03。真机上这张码应渲染成二维码，由自助机或手机扫。现在的做法让"扫码"这一步在演示中退化成"点按钮"，评审时容易被认为是没做扫码——实际令牌签发与验签是完整的，缺的只是前端的二维码渲染（引入一个 QR 库即可）。

**3. 没有响应式断点。** `style.css` 里没有任何 `@media`，座位网格固定 `repeat(10, 1fr)`，页面最大宽度 1040px。在 375px 宽的手机上，每格约 30px，座位号（A-01，14px 加粗）会溢出，特征文字（靠窗/插座，11px）完全挤掉。而签到的主要场景恰恰是手机。表11 承诺"适配移动端"，实现上没有兑现，这一条应记为未达标而不是"未验证"。

## 六、刻意没做的部分

- **管理端界面**：UC-07、UC-08 只有接口，管理员视角的页面一张没做。原因是三周内优先保住判定链路的正确性，界面的投入产出比最低。演示时用脚本直接调接口，验收脚本里的 FT-09 就是这么做的。
- **错误态与空态**：座位图为空、接口超时、网络断开，都只有提示条一行字，没有骨架屏或重试按钮。演示环境在同一台机器上跑，网络问题不出现，所以没做。
- **通知已读**：通知区把未读项高亮，但没有"标记已读"的入口，服务端也没有对应接口，`read` 字段永远是 false。高亮的语义因此退化成"所有通知都是新的"。
- **多预约单管理**：一次只显示一张卡片，第二张会覆盖第一张。要支持同时持有多张预约，需要把卡片改成列表，这是结构改动，不是样式调整。

## 七、这版原型验证了什么

从需求侧看，这版原型至少验证了三件事，都是纸面推演得不到的：

1. **五种状态是必要的**。最初只打算做"空闲/占用"两态，做完发现"暂离"无法归类——归到占用会让暂离座位看起来像被人正常使用，归到空闲会诱导别人来抢。斜纹方案是被原型逼出来的。
2. **空闲计数必须常驻在顶部**。随机型学生（先看哪层有空）的路径是"扫一眼数字 → 决定去不去"，如果数字藏在座位图里，等于没做。
3. **"我的预约"不能是独立页面**。学生真正需要的是"我这一单现在什么状态、下一步该干什么"，这正是卡片上那五个按钮回答的问题；单独的列表页只回答"我约过什么"，对当前这一单没有帮助。

这三条后来都写进了报告 3.2 的用例描述，属于"原型反过来修正需求"的部分。

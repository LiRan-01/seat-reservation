# 设计与数据模型补充说明

> 撰写：刘雨可（系统分析与设计）
> 对应报告：第 4 章 系统分析与设计

## 一、设计取舍

后端按领域驱动的方式分了四层：`domain`（实体与枚举）、`repo`（Spring Data JPA 接口）、`service`（业务规则）、`web`（REST 控制器）。这样做的原因是本项目的核心逻辑集中在“状态怎么迁移、并发怎么互斥”，把规则收在 service 层，控制器只做参数解析与响应组装，改规则时不用碰接口层。

## 二、表结构的关键约束

1. `reservation` 上有唯一键 `uk_seat_start(seat_id, start_time)`：这是并发预约的最后一道防线。行锁解决的是“同时查到空位”，唯一键解决的是“两个事务都通过了校验”的极端情况，两者缺一不可；
2. `violation` 上有唯一键 `uk_res_type(reservation_id, type)`：保证同一张预约的同一类违规只扣一次分，定时任务重复执行也不会重复扣分；
3. `reservation` 的 `status + end_time` 建了联合索引 `idx_status_end`，定时任务按状态与截止时间扫描时走索引，实测 500 条数据的扫描耗时约 1.4 秒。

## 三、状态机落地方式

状态迁移统一用“条件更新”实现：`update reservation set status = :to where id = :id and status = :from`，只有影响行数为 1 才继续后续动作（释放座位、写违规、通知候补）。这样即使定时任务被并发触发，也不会把同一张预约处理两次。

## 四、并发方案的验证

设计阶段判断“行锁 + 唯一键”足够覆盖抢座场景，实测也验证了这一点：200 次抢座请求落在 40 个座位上，成功 40、冲突 160、超卖 0。

但座位图接口没有做批量优化，按座位逐条查询占用情况，30 并发下 P95 为 350 ms，超出 200 ms 目标。改造方向是把“某房间某时段的占用”改成一次查询返回座位集合，前端合并状态，这项已作为 BUG-05 记录在报告表 21。

报告 2.1—2.3 与第 3 章由我负责，落到四份东西：干系人与用户画像、典型场景、现有方案对比（2.1—2.3）；业务流程、用例图、用例清单 UC-01—UC-10 与两条核心用例的详细描述（3.1—3.2）；非功能指标（3.3）；需求追踪关系（3.4）。学生端主流程的界面原型也由我出，后来落到 `frontend/src/App.vue` 一个单页上。

## 二、访谈之后改掉的三个判断

1. **学生要的不是"有座位"，是"确定有"**。初稿把痛点写成座位不足，走访两个自习室后发现供给并不总是瓶颈，真正的问题是"看到空位也可能是被占的"。这一条直接导致座位图要区分"空闲/已预约/使用中/暂离/停用"五种状态，而不是简单标个空或满。
2. **管理员的诉求是"有据可依"**。管理员不愿意处置占座，不是懒，是怕争执时无法举证。所以违规必须落库、必须能申诉，UC-06 的判定结果不能只发通知就完事。
3. **预约本身不解决问题**。把预约搬到线上只是把占座合法化了，只有"签到才让资源生效"才能闭环。这条决定了 UC-03 是必须级，且签到窗口必须有上下界——只卡下界，约了不来照样占座；只卡上界，提前一小时来也算到。

## 三、用例落到哪个接口

| 用例 | 接口 | 实现上的关键约束 |
|---|---|---|
| UC-01 | `GET /api/rooms/{roomId}/seats?start=&end=` | 返回 `status` 与 `busy`，`busy` 由 `countOverlap` 按座位逐个判断 |
| UC-02 | `POST /api/reservations` | 三重校验（时段冲突、信用门槛、当日次数），唯一键 `uk_seat_start` 兜底，冲突统一 `TIME_CONFLICT` |
| UC-03 | `POST /api/checkin` | 只收 `token` 与 `deviceId`，**不收 seatId**，座位从令牌里解析 |
| UC-04 | `POST /api/reservations/{id}/away?minutes=30`、`/back` | 暂离是 `USING` 的子状态，不释放座位 |
| UC-05 | `POST /api/waitlist`、`GET /api/notifications` | 释放后按登记顺序通知首位，保留优先权 |
| UC-06 | `ReleaseJob` 每分钟扫描 | 条件更新，影响行数为 0 直接跳过 |
| UC-08 | `POST /api/reservations/{id}/release?reason=` | 释放时同步把预约改成 `FORCED` |
| UC-10 | `GET /api/stats/occupancy?from=&to=` | 上座率 = 有效预约占用时长 /（座位数 × 开放时长 08:00—22:00） |

UC-03 之所以坚持"只收令牌不收座位号"，是因为一旦前端能指定座位，只要拿到别人的签到码就能替人签到，用例描述里的 A2 异常流就失效了。令牌由 `CodeSigner` 签名，座位与预约信息全部从令牌解析，调用方无法指定。

## 四、两条异常流后来变成了缺陷

用例描述里写死的两条约束，正是第 6 章里两个缺陷的根因：

- **A2 令牌重放**：写成"一次性随机数写入缓存，重复提交直接拒绝"，实测对应 ET-02；
- **B1 任务幂等**：写成"以影响行数判断是否继续，不得先查后改"，这正是 BUG-01（同一预约被扣两次分）的修复依据。

反过来说，BUG-04（强制释放后原预约仍可签到）是我用例描述里漏掉的：UC-08 只写了"释放座位"，没写"同步终止预约单"，接口就只改了座位状态。

## 五、非功能指标怎么定的，以及差在哪

指标按两个自习室实测峰值外推：单校区约 2000 个座位、日预约约 8000 单，早八与午后各集中了四成日单量，据此取峰值 200 并发、预约 P95 300 ms。

两处没有落到位，如实记在这里：

- **座位图 200 ms 未达标**：`docs/实测结果/perf.txt` 里几次运行在 320—390 ms 之间，原因是 UC-01 的实现按座位逐个查占用，形成 N+1；需求里只写了"座位图不超过 200 ms"，没把查询口径（一次查完还是逐座位查）约束进接口设计，已记为 BUG-05；
- **签到码有效期**：表 10 写的是"10 分钟且一次性"，实现里 `application.yml` 的 `checkin-code-minutes` 配的是 120 分钟。初衷是覆盖跨时段长预约的签到需求，但和需求文档不一致，需要统一口径——要么改配置，要么改指标。

另外，表 10 里"JWT 鉴权与 RBAC 授权"这一条本期没有在应用内实现：按 1.3 的边界，认证交由学校统一身份认证承担，应用只接收 `userId`，代码里只有签到码签名，没有鉴权过滤器。这一点在报告边界说明里写了，但指标表里没标"由外部承担"，容易被误读为已实现。

## 六、没做到的部分

- 管理端只有接口没有界面，UC-07—UC-10 在前端没有对应页面，演示时用脚本直接调接口；
- UC-09 只做了扣分与阈值拦截（`credit-threshold: 60`、`violation-score: -5`），申诉工单流程没有实现，报告中标的是"可以"级；
- 界面原型只覆盖学生端主流程（选室 → 座位图 → 预约 → 签到 → 暂离/返回），管理端巡查处置场景没有原型；
- 前端没有自动化 UI 测试，座位图交互靠手工点击验证。

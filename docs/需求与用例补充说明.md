## 二、访谈之后改掉的三个判断

1. **学生要的不是"有座位"，是"确定有"**。初稿把痛点写成座位不足，走访两个自习室后发现供给并不总是瓶颈，真正的问题是"看到空位也可能是被占的"。这一条直接导致座位图要区分"空闲/已预约/使用中/暂离/停用"五种状态，而不是简单标个空或满。
2. **管理员的诉求是"有据可依"**。管理员不愿意处置占座，不是懒，是怕争执时无法举证。所以违规必须落库、必须可追溯，UC-09 的判定结果不能只发通知就完事。
3. **预约本身不解决问题**。把预约搬到线上只是把占座合法化了，只有"签到才让资源生效"才能闭环。这条决定了 UC-03 是必须级，且签到窗口必须有上下界——只卡下界，约了不来照样占座；只卡上界，提前一小时来也算到。

## 三、用例清单落到哪个接口

编号与报告表7 的用例清单一一对应，共 13 条：

| 用例 | 接口 | 实现上的关键约束 |
|---|---|---|
| UC-01 浏览座位与预约 | `GET /api/rooms/{roomId}/seats?start=&end=` | 返回 `status` 与 `busy`，`busy` 由 `countOverlap` 按座位逐个判断 |
| UC-02 创建预约 | `POST /api/reservations` | 已实现两道校验（`countOverlap` 时段冲突、`creditThreshold` 信用门槛），当日次数上限未实现（见第六节）；唯一键 `uk_seat_start` 兜底，冲突统一 `TIME_CONFLICT` |
| UC-03 扫码签到 | `POST /api/checkin` | 只收 `token` 与 `deviceId`，**不收 seatId**，座位从令牌里解析 |
| UC-04 暂离与返回 | `POST /api/reservations/{id}/away?minutes=30`、`/back` | 暂离是 `USING` 的子状态，不释放座位 |
| UC-05 候补登记 | `POST /api/waitlist` | 释放后按登记顺序通知首位，保留优先权 |
| UC-06 查看我的预约 | `GET /api/reservations?userId=` | 只读；按时间倒序返回本人预约。当前实现是全表加载后按 `userId` 过滤，数据量上来后需改为带索引的查询 |
| UC-07 强制释放 | `POST /api/reservations/{id}/release?reason=` | 条件更新为 `FORCED`，座位回 `AVAILABLE`，并触发候补通知 |
| UC-08 查看统计 | `GET /api/stats/occupancy?from=&to=` | 上座率 = 有效预约占用时长 /（座位数 × 开放时长 08:00—22:00） |
| UC-09 自动超时释放 | `ReleaseJob` 每分钟扫描 | 条件更新，影响行数为 0 直接跳过 |
| UC-10 统一身份认证（演示版） | 无独立接口 | 演示版以 `userId`/学号参数代替，正式上线对接学校统一身份认证 |
| UC-11 用户取消 | `POST /api/reservations/{id}/cancel?userId=` | 校验只能取消本人预约，且仅 `RESERVED` 可取消 |
| UC-12 正常结束 | `POST /api/reservations/{id}/finish` | 非终态置 `RELEASED`，释放座位并通知候补，不计违规 |
| UC-13 查看通知 | `GET /api/notifications?userId=` | 候补叫号等站内通知，按 `userId` 查询 |

UC-03 之所以坚持"只收令牌不收座位号"，是因为一旦前端能指定座位，只要拿到别人的签到码就能替人签到，用例描述里的 A2 异常流就失效了。令牌由 `CodeSigner` 签名，座位与预约信息全部从令牌解析，调用方无法指定。

UC-07 与 UC-12 共用"释放座位 + 通知候补"这条尾链，区别在终态：强制释放落 `FORCED`，正常结束落 `RELEASED`，两者都不记违规；只有 UC-09 的超时释放写 `violation` 并扣分。早期描述里"强制释放并计违规"与实现不符，已在第四节更正。

## 四、两条异常流后来变成了缺陷，一条描述与实现不符

用例描述里写死的两条约束，正是第 6 章里两个缺陷的根因：

- **A2 令牌重放**：写成"一次性随机数写入缓存，重复提交直接拒绝"，实测对应 ET-02；
- **B1 任务幂等**：写成"以影响行数判断是否继续，不得先查后改"，这正是 BUG-01（同一预约被扣两次分）的修复依据。

反过来说，BUG-04（强制释放后原预约仍可签到）是我用例描述里漏掉的：UC-07 只写了"释放座位"，没写"同步终止预约单"，接口就只改了座位状态。

**第三条是反向的：描述写了，实现没做。** UC-07 的早期版本写"强制释放并记录违规"，而 `forceRelease()` 只做三件事——置 `FORCED`、座位回 `AVAILABLE`、通知候补，不写 `violation`、不动信用分。当时以为是实现漏了，核对后确认是有意的取舍：强制释放依据的是管理员现场核验，存在误判（学生只是去接水），罚错比不罚更难收拾。产品结论是"只释放、不罚分"，文档按实现改正。这条留在报告外的原因是报告表7 对 UC-07 的简述只写了"执行强制释放并填写原因"，没有涉及计分，正文不必改；但用例规格本身要说清，否则后来维护的人会照旧描述去补违规写入。

## 五、非功能指标怎么定的，以及差在哪

指标按两个自习室实测峰值外推：单校区约 2000 个座位、日预约约 8000 单，早八与午后各集中了四成日单量，据此取峰值 200 并发、预约 P95 300 ms。

一处没有落到位，如实记在这里：

- **座位图 200 ms 未达标**：`docs/实测结果/perf.txt` 里几次运行在 320—390 ms 之间，原因是 UC-01 的实现按座位逐个查占用，形成 N+1；需求里只写了"座位图不超过 200 ms"，没把查询口径（一次查完还是逐座位查）约束进接口设计，已记为 BUG-05。

另外两处早期的不一致，已在 11-27 的报告修订中对齐：表11 的安全一条原写"签到码有效期 10 分钟"，现改为 **120 分钟**，与 `application.yml` 的 `checkin-code-minutes` 一致；原稿还写有"JWT 鉴权与 RBAC 授权"，与实现不符（应用内没有鉴权过滤器，认证按 1.3 的边界交外部承担），该条已从指标表中移除，现在的"安全"一条只承诺 HMAC 签名与一次性随机数防重放，与代码一致。

九项指标的逐条验证结论见《非功能需求与验证矩阵.md》，那里把"达标／未达标／未验证"分开标了，避免笼统地写成全部通过。

## 六、没做到的部分

- **UC-02 的"当日次数上限"未实现**：`ReservationService.reserve()` 只有时段冲突与信用门槛两道校验，没有按用户统计当日已约单量，同一学生在同一天可以对多个不同座位下单。需求里写了这条，但没落到接口约束上，属于需求到实现的漏转；
- 管理端只有接口没有界面，UC-07、UC-08 在前端没有对应页面，演示时用脚本直接调接口；
- 信用申诉在 2.3 划为 Won't，用例清单里没有对应条目；UC-09 只做到扣分与阈值拦截（`credit-threshold: 60`、`violation-score: -5`）；
- 界面原型只覆盖学生端主流程（选室 → 座位图 → 预约 → 签到 → 暂离/返回），管理端巡查处置场景没有原型；
- 前端没有自动化 UI 测试，座位图交互靠手工点击验证。

核对代码后补记的五条，都属于"用例规格写了、实现漏了"的同类问题，一并列出以免失传：

- **候补重复登记未去重**：同一学生对同一座位可反复登记，队列里会出现多条自己人，被通知时只取最早一条，其余继续占位（UC-05 异常流 A2）；
- **统计把已取消的预约计入有效**：`StatsController` 只剔除 `RELEASED`／`FORCED`／`NO_SHOW`，漏了 `CANCELLED`，上座率偏高（UC-08 口径偏差之一）；
- **取消接口的归属校验可绕过**：`cancel()` 里写的是"`userId` 不为空才校验"，不带参数即可取消他人预约，正式版必须强制；
- **暂离上限配置未生效**：`app.away-max-minutes: 30` 与代码里的 `Math.min(minutes, 30)` 重复定义，改配置不改行为；
- **结束接口对未签到的预约也放行**：会给未签到预约落 `RELEASED` 而不是 `CANCELLED`，与 UC-11/UC-12 的语义边界不一致，统计口径因此受影响。

如果补测，优先级最高的是 UC-11 取消：它是唯一一条带归属校验（`USER_MISMATCH`）的用例，也是最容易写错权限的一条，目前完全没有测试覆盖。
